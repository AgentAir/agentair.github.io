AlmaLinuxのrsyslogログをSambaとRobocopyでWindowsへ定期コピーする

2026-08-05 / Network Automation / Linux / Syslog

Home Articles About

はじめに

ネットワーク機器からAlmaLinuxへ集約したSyslogを、機器IPごとのフォルダー構成を保ったままWindows 11へ定期コピーした検証記録です。当初はAlmaLinuxからWindows上のNXLogへSyslogを再転送する構成を考えましたが、転送されるのはログメッセージであり、AlmaLinux上のフォルダー構成ではないことに気付きました。

そこで、rsyslogが作成したファイルをSambaで読み取り専用共有し、WindowsからRobocopyを1時間ごとに実行する構成へ変更しました。この記事では、設定手順だけでなく、構成を見直す中で理解が変わった点と、ACLや文字コードで詰まった点も残します。掲載するIPアドレスはすべてドキュメント用です。

構成

最終的な構成は次のとおりです。

ネットワーク機器
    ↓ UDP/514
AlmaLinux rsyslog
    ↓
/var/log/remote/<機器IP>/<日付>.log
    ↓ Samba共有
Windows 11
    ↓ 1時間ごとにRobocopy
C:\Syslog\remote\<機器IP>\<日付>.log

AlmaLinuxはSyslogの受信と一時保管を担当し、Windowsはコピー済みログの長期保管先として使います。Samba共有は読み取り専用とし、Windows側からAlmaLinux上のログを変更しない構成にしました。

最初に検討したNXLog転送

当初は、次のようにAlmaLinuxからWindows 11上のNXLogへUDP Syslogを転送する構成を検討しました。

ネットワーク機器 → AlmaLinux → NXLog

Windows側のNXLogでは、送信元アドレスを使って保存先ファイルを決めていました。

File 'C:\\Syslog\\' + $MessageSourceAddress + '.log'

この設定なら送信元ごとにファイルが分かれるように見えます。しかし、NXLogへ直接パケットを送信するのは元のネットワーク機器ではなくAlmaLinuxです。そのため、NXLogから見た送信元はAlmaLinuxのIPアドレスになります。 

C:\Syslog\192.0.2.10.log

なぜNXLog転送をやめたのか

rsyslogのSyslog転送はログメッセージを次の受信先へ送る仕組みです。次のようなローカルのフォルダー構成を、そのまま転送先へ引き継ぐ仕組みではありません。 

/var/log/remote/<機器IP>/<日付>.log

元の機器IPをメッセージ内へ追加してNXLog側で再解析する設計も考えられますが、今回はすでにrsyslogが期待どおりのフォルダーとファイルを作成しています。目的はその構成を維持してWindowsへ保管することなので、ファイルをそのままコピーするほうが分かりやすいと判断しました。

この理解からNXLogへの再転送をやめ、Samba共有とRobocopyを使う構成へ変更しました。

AlmaLinuxのrsyslog設定

/etc/rsyslog.d/remote.confへ次の設定を記載しました。

module(load="imudp")

template(
    name="RemoteHostDateLogs"
    type="string"
    string="/var/log/remote/%FROMHOST-IP%/%$now%.log"
)

ruleset(name="remote") {
    action(
        type="omfile"
        dynaFile="RemoteHostDateLogs"
        createDirs="on"
    )
}

input(
    type="imudp"
    port="514"
    ruleset="remote"
)
設定 役割
module(load="imudp") imudpモジュールを読み込み、UDP Syslogを受信できるようにする
template 機器IPと日付を使って保存先パスを組み立てる
%FROMHOST-IP% rsyslogが受信したSyslogの送信元機器IP
%$now% rsyslogが処理した現在の日付
omfile ruleset内でログをローカルファイルへ保存する
input() rulesetの外側に記載し、UDP/514の入力を定義する
ruleset="remote" 受信したログをremote rulesetへ渡す

構文を確認してからrsyslogを再起動し、状態を確認しました。

sudo rsyslogd -N1
sudo systemctl restart rsyslog
sudo systemctl status rsyslog --no-pager

Samba共有の構築

Samba本体に加え、ACLとSELinuxの確認に使うパッケージをインストールしました。

sudo dnf install -y samba samba-client acl policycoreutils-python-utils

共有参照専用のLinuxユーザーを作成し、続けてSambaユーザーとして登録しました。

sudo useradd -M -s /sbin/nologin syslogcopy
sudo smbpasswd -a syslogcopy
  • -Mはホームディレクトリを作成しない指定
  • /sbin/nologinは、このユーザーによるOSへのログインを禁止する指定
  • Linuxユーザーの作成とSambaユーザーの登録は別の操作
  • syslogcopyはSamba共有を参照するためだけに使うユーザー

パスワードは対話入力し、記事やスクリプトには保存していません。

/etc/samba/smb.confへ次の共有設定を追加しました。

[remote]
    path = /var/log/remote
    browseable = yes
    read only = yes
    valid users = syslogcopy

角括弧内のremoteが共有名です。したがって、Windowsからの接続先は次のUNCパスになります。 

\\192.0.2.10\remote

Samba設定を確認し、サービスを有効化・起動しました。

sudo testparm -s
sudo systemctl enable --now smb
sudo systemctl status smb --no-pager

firewalldではSambaサービスを許可しました。

sudo firewall-cmd --permanent --add-service=samba
sudo firewall-cmd --reload
sudo firewall-cmd --list-services

ACLでアクセス拒否を解決

WindowsからSamba共有へ接続したところ、「アクセス許可がない」と表示されました。Samba側でread only = yesと設定しても、Linux側のファイル権限を超えて読み取れるわけではありません。

次のACLを設定したところ、syslogcopyで共有を参照できるようになりました。

sudo setfacl -R -m u:syslogcopy:rX /var/log/remote
sudo setfacl -m d:u:syslogcopy:rX /var/log/remote
  • 1行目は、すでに存在するファイルとフォルダーへsyslogcopyの権限を付ける
  • 2行目は、今後作成されるファイルとフォルダーへ既定ACLを継承させる
  • rXはファイルの読み取りと、ディレクトリをたどるために必要な実行権限を与える

ACLと専用ユーザーからの参照可否は次のコマンドで確認しました。

sudo getfacl /var/log/remote
sudo -u syslogcopy ls -l /var/log/remote

今回の環境では、ACL設定後にWindowsから参照可能になりました。SELinuxの設定を変更したとは断定できないため、SELinuxは次のコマンドで状態を確認し、問題が残る場合の切り分け対象とします。 

getenforce
getsebool samba_export_all_ro

SELinuxがEnforcingで読み取り共有を拒否する環境では、影響と組織のポリシーを確認したうえで、sudo setsebool -P samba_export_all_ro onの設定を検討します。今回この設定を実施した、という意味ではありません。

Windowsから共有を確認

エクスプローラーまたは「ファイル名を指定して実行」から次のパスを開き、Sambaへ登録したsyslogcopyの資格情報で接続しました。 

\\192.0.2.10\remote

機器IPのフォルダーと日付ごとのログが表示され、ファイルを読み取れることを確認します。共有は読み取り専用なので、Windows側からの作成・更新・削除はできない設計です。

RobocopyのBAT作成

C:\Scripts\copy_syslog.batとして次のBATファイルを保存しました。

@echo off
setlocal

set "SOURCE=\\192.0.2.10\remote"
set "DEST=C:\Syslog\remote"
set "LOG=C:\Syslog\robocopy.log"

robocopy "%SOURCE%" "%DEST%" /E /Z /FFT /R:3 /W:10 /COPY:DAT /DCOPY:T /LOG+:"%LOG%"

set "RESULT=%ERRORLEVEL%"

if %RESULT% GEQ 8 exit /b %RESULT%
exit /b 0
オプション 意味
/E空フォルダーを含むすべてのサブフォルダーを確認対象にする
/Z中断したコピーを再開できる再起動可能モードでコピーする
/FFTファイル時刻の比較精度を2秒にし、異なるファイルシステム間の時刻差を吸収する
/R:3失敗時の再試行回数を3回にする
/W:10再試行まで10秒待つ
/COPY:DATファイルのデータ、属性、タイムスタンプをコピーする
/DCOPY:Tディレクトリのタイムスタンプをコピーする
/LOG+実行結果を既存のログファイルへ追記する

当初、日本語のフォルダー名をBAT内で使ったところ、BATの文字コードとの組み合わせにより、文字化けした名前のフォルダーが作成されました。今回の保存先は、文字コードの影響を避けるため英数字のremoteにしました。

Robocopyの差分判定を理解する

/Eは、毎回すべてのファイルを無条件にコピーする指定ではありません。空フォルダーを含む全階層を確認対象にする指定です。 

/E
→ 空フォルダーを含む全階層を確認対象にする

そのうえでRobocopyがコピー元とコピー先を比較し、ファイルごとに処理を決めます。

同じファイル  → スキップ
新規ファイル  → コピー
更新ファイル  → ファイル単位で再コピー

これはファイル内部の追加部分だけを送るrsync形式の差分転送ではありません。Robocopyはファイル単位で差分を判定し、更新されたファイルはそのファイルを再コピーします。 

AlmaLinux：A.log、更新されたB.log、新規C.log
Windows  ：A.log、古いB.log

実際にコピーされるもの：
B.log、C.log

Windows側の古いログが消えない理由

今回のBATには、コピー先を同期・削除する次のオプションを付けていません。

/MIR
/PURGE
/MOVE
/MOV

そのため、AlmaLinux側で古いログが削除されても、Windowsへコピー済みのログは残ります。

最初：
AlmaLinux：A
Windows  ：A

1週間後：
AlmaLinux：B、C
Windows  ：A

Robocopy後：
Windows  ：A、B、C

/MIRまたは/PURGEを使うと、コピー元に存在しないファイルがコピー先からも削除されます。Windows側へログを残す今回の用途では使用しません。

Robocopyの終了コード

Robocopyの終了コードは、一般的なコマンドのように「0以外はすべて失敗」ではありません。0～7は正常または警告を含む成功、8以上はコピー失敗を含む結果です。

BATではRobocopy直後の%ERRORLEVEL%を保存し、0～7なら正常終了の0へ変換してタスクスケジューラへ返します。8以上は元の終了コードを返すため、失敗として確認できます。

実行ログはC:\Syslog\robocopy.logへ追記されます。

Get-Content C:\Syslog\robocopy.log -Tail 50

タスクスケジューラで1時間ごとに実行

管理者権限のコマンドプロンプトで、1時間ごとにBATを実行するタスクを登録しました。

schtasks /create /tn "Syslog Copy" /tr "C:\Scripts\copy_syslog.bat" /sc hourly /mo 1 /st 00:00 /it /f
オプション意味
/create新しいタスクを作成する
/tn "Syslog Copy"タスク名を指定する
/tr実行するBATファイルを指定する
/sc hourly時間単位のスケジュールにする
/mo 11時間ごとに実行する
/st 00:00開始時刻を0時にする
/it対象ユーザーがログオンしているときだけ対話型で実行する
/f同名タスクがある場合に確認なしで上書きする

/itがあるため、対象ユーザーがWindowsへログオンしている間だけ実行されます。ログオフ中も確実にコピーする必要がある場合は、実行アカウントや資格情報の扱いを含め、別のタスク設定を検討する必要があります。

登録内容の確認と手動実行は次のコマンドで行います。

schtasks /query /tn "Syslog Copy" /v /fo list

schtasks /run /tn "Syslog Copy"

PowerShellでは、最終実行結果と次回実行時刻も確認できます。

Get-ScheduledTask -TaskName "Syslog Copy"
Get-ScheduledTaskInfo -TaskName "Syslog Copy" |
    Format-List LastRunTime, LastTaskResult, NextRunTime

AlmaLinux側のログを週1回削除

AlmaLinux側の保管量を抑えるため、rootのcrontabを編集しました。

sudo crontab -e
30 3 * * 0 /usr/bin/find /var/log/remote -type f -delete && /usr/bin/systemctl restart rsyslog

この設定の意味は次のとおりです。

毎週日曜日の3時30分
/var/log/remote配下の全ファイルを削除
機器IPのフォルダーは残す
削除後にrsyslogを再起動

これは「7日より古いファイルだけを削除」する設定ではありません。週次実行時点で/var/log/remote配下に存在するすべてのファイルを削除します。

Robocopyには/MIRと/PURGEがないため、AlmaLinux側で削除してもWindows側のコピー済みログは残ります。一方、Windowsが長期間停止してRobocopyが実行されなかった場合は、Windowsへコピーされる前にAlmaLinux側でログが削除される可能性があります。必要な保管期間と停止時間を考慮して、削除間隔を決める必要があります。

設定確認コマンド

各レイヤーの確認コマンドをまとめます。

AlmaLinux

sudo rsyslogd -N1
sudo systemctl status rsyslog --no-pager
sudo testparm -s
sudo systemctl status smb --no-pager
sudo firewall-cmd --list-services
sudo getfacl /var/log/remote

sudo crontab -l
sudo systemctl status crond --no-pager

Windows 11

Get-Content C:\Syslog\robocopy.log -Tail 50

    Format-List LastRunTime, LastTaskResult, NextRunTime

確認は、rsyslogがファイルを作成できているか、syslogcopyがLinux上で読み取れるか、Windowsから共有を参照できるか、Robocopyがコピーできるか、タスクが予定どおり動くか、の順に分けると切り分けやすくなります。

設定を削除・元に戻す方法

検証を終了する場合は、対象を確認したうえで、追加した設定をレイヤーごとに戻します。

Windowsのタスクを削除

schtasks /delete /tn "Syslog Copy" /f

BATファイル、Windowsへコピー済みのログ、Robocopyログは、このコマンドでは削除されません。必要性と保存要件を確認して個別に扱います。

AlmaLinuxのcronを削除

sudo crontab -eを実行し、今回追加した次の1行だけを削除します。

30 3 * * 0 /usr/bin/find /var/log/remote -type f -delete && /usr/bin/systemctl restart rsyslog

Samba共有を停止・削除

/etc/samba/smb.confから[remote]セクションを削除し、設定確認後にSambaを再起動します。Samba自体が不要なら無効化します。

sudo testparm -s
sudo systemctl restart smb

# Samba自体を使わなくなる場合
sudo systemctl disable --now smb
sudo firewall-cmd --permanent --remove-service=samba
sudo firewall-cmd --reload

共有専用ユーザーが不要になった場合は、Samba登録を削除してからLinuxユーザーを削除します。

sudo setfacl -R -x u:syslogcopy /var/log/remote
sudo setfacl -x d:u:syslogcopy /var/log/remote
sudo smbpasswd -x syslogcopy
sudo userdel syslogcopy

rsyslog設定を戻す

/etc/rsyslog.d/remote.confが今回の検証専用であることを確認して削除または退避し、構文確認後にrsyslogを再起動します。別の受信設定と共用している場合は、今回追加した部分だけを戻します。 

sudo rsyslogd -N1
sudo systemctl restart rsyslog

/var/log/remote内のログは設定を戻しても自動では消えません。削除は取り返せないため、コピー済みか、保管が不要かを確認してから別途判断します。

今回の学び

  • Syslog転送はログメッセージを送る仕組みであり、フォルダーを転送する仕組みではない
  • AlmaLinuxで中継すると、NXLogから見た直接の送信元はAlmaLinuxになる
  • 元のフォルダー構成を維持するなら、作成済みファイルをコピーする方法が分かりやすい
  • Sambaは共有設定だけでなく、Linux側のファイル権限やACLも必要
  • /Eは全階層を確認する指定であり、毎回全ファイルをコピーする指定ではない
  • Robocopyの差分判定はファイル単位であり、ファイル内部の差分だけを送る方式ではない
  • /MIRと/PURGEを付けなければ、コピー元で消えたログはWindows側に残る

まとめ

AlmaLinuxのrsyslogで機器IPと日付ごとに保存したログを、Sambaの読み取り専用共有とRobocopyでWindows 11へ定期コピーできました。NXLogへの再転送では元のフォルダー構成を引き継げないと理解したことが、構成を見直すきっかけでした。

Robocopyは全階層を確認しながらファイル単位で差分を判定し、削除同期オプションを付けなければWindows側の過去ログを残せます。ただし、AlmaLinux側の週次削除より前にコピーが実行されることが前提です。運用ではRobocopyログとタスクの実行結果を確認し、Windows停止期間とAlmaLinux側の保管期間が矛盾しないように設計します。
